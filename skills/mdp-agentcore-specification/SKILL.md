# MDP.AgentCore 功能規格

流程與文件格式的全文在 [references/specification.md](references/specification.md)，這是給人看的文件，也是規則的唯一來源。本檔只說明怎麼使用它。

## 使用方式

0. **先判斷要不要走本流程**：錯誤修正與不改變商業規則的小幅調整（文字、標籤、選項、欄位順序、樣式）直接改程式碼，不建立 specs；拿不定時問使用者。細節見 references 第 1 章「什麼時候不走本流程」。

1. **判斷使用者要的是哪個階段**，只做那個階段：

   | 使用者要求 | 階段 | 讀的章節 |
   |---|---|---|
   | 新功能、需求、使用者故事、驗收條件 | 需求分析（01-requirement.md） | 1、2、3 |
   | 系統設計、物件模型 | 系統設計（02-design.md） | 1、4 |
   | 任務拆解、實作順序 | 任務拆解（03-tasks.md） | 1、5 |
   | 實作全部任務或某個任務（Tn） | 程式開發 | 1、6 |
   | 修改某份文件 | 該文件 | 1 與該文件的章節 |

2. **做完這個階段就停**。不要自行開始下一份文件或下一個任務，即使你覺得某些內容屬於下一份；最多在回覆最後提醒一句「下一步可以做什麼」，由使用者決定。

3. **設計與實作前，找出專案技術並套用對應的架構規範**：

   | 專案裡有 | 架構規範 |
   |---|---|
   | `.sln`、`.csproj` | `mdp-netcore-architecture` |
   | `pom.xml`、`build.gradle` | `mdp-javacore-architecture` |
   | `package.json` 含 vue | `mdp-vuecore-architecture` |
   | `pyproject.toml`、`requirements.txt` | `mdp-pythoncore-architecture` |

   前後端都有時兩個都套用。02-design.md 的物件模型（Entity、Repository、Context 這類物件的職責與寫法）和實作的程式碼都必須符合架構規範；規格文件只決定「做什麼」，架構規範決定「怎麼寫」。若對應的架構 Skill 不存在，告訴使用者，並依專案現有程式碼的寫法設計。

4. **以目前的程式碼為準**：寫「對既有行為的影響」之前，實際讀相關的程式碼並引用檔案名稱。專案 `CLAUDE.md` 有本專案特有的補充（例如頁面結構、指令）時一併遵守。

5. **遇到缺漏或矛盾就停下來問**：前一份文件沒寫的行為不自行補上；需求沒定的事放進「待決事項」或「待確認事項」，不假設答案。

6. **每個階段都要有測試案例；後面的階段改到前面的文件時，跑過每個階段的測試案例**（文件比對＋執行測試），細節見 references 第 1 章。

## 用語

- 「**功能規格**」指 `specs/` 底下的文件，也可以直接稱需求分析、系統設計、任務拆解。
- 「**架構規範**」指 `*-architecture` Skill。兩者不要混稱。
