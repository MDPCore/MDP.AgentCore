# MDP.AgentCore 功能規格

以 AI Agent 開發新需求的流程：先把需求、設計、任務寫成文件，再依任務實作。每份文件都要使用者明確要求才開始，避免 AI 自行假設需求或擴大範圍。

本流程與技術無關；設計與實作時遵守專案技術對應的架構規範（`mdp-netcore-architecture`、`mdp-javacore-architecture`、`mdp-vuecore-architecture`、`mdp-pythoncore-architecture`）。

## 1. 流程

```
需求分析 ──────────▶ 系統設計 ─────▶ 任務拆解 ─────▶ 程式開發
01-requirement.md    02-design.md    03-tasks.md     一次一個任務
```

- **依序產出**，後一份以前一份為依據。
- **沒有核准步驟**：由使用者決定何時進入下一份文件或實作。AI 只在使用者明確要求時才開始下一份，即使某些內容「應該寫在下一份」，也只能提醒，不能自己開始。文件裡也不寫核准狀態。每份文件都要經過使用者審核來回，AI 自行往前推進會讓未定案的內容被當成依據。
- **不自行補規格**：前一份文件有缺漏或矛盾時，停下來問使用者，不自行假設、不擴大範圍。
- **每個階段建議開新對話**，只帶著定稿的文件進入下一階段，避免把討論中被否決的想法帶進去。
- **規格以外的需求不在實作時臨時加**：先回頭修改 01／02，再實作。
- **每個階段都必須有測試案例**，缺一份就不算完成：

  | 階段 | 測試案例 |
  |---|---|
  | 01-requirement.md | 驗收條件（`AC-n.m`，Given／When／Then） |
  | 02-design.md | `### 6. 測試`：每條 AC 都對應到單元測試或手動驗收 |
  | 03-tasks.md | 每個任務的單元測試與手動驗收 |
  | 程式開發 | 執行上述測試案例 |

  每個階段都要能檢查是否忠實承接前一個階段；沒有測試案例，後面的階段改到它時也無從驗證有沒有改壞。
- **後面的階段改動前面的階段時，必須跑過每個階段的測試案例**（例如寫 02 時改了 01，或實作時改了 02）。改完前面的文件後：
  1. **文件比對**：逐條比對 01 的 AC → 02 的 `### 6. 測試` → 03 的任務測試案例，確認每條仍有對應、沒有矛盾；下游文件跟著修改，並列出改了哪些地方。
  2. **執行測試**：已經實作的部分，執行全部單元測試，並逐項回報所有已完成任務的手動驗收結果（AI 無法執行的，列出來請使用者驗收）。

  全部通過才繼續原本的階段；有不一致或失敗時先修正。只檢查被改的那一份，看不出下游文件與既有程式碼是否因此失準。
- 文件一律以**繁體中文**撰寫。

### 錯誤要加上測試保護

**發生過的錯誤要加上測試保護。** 修正錯誤時，同時加上一項能重現這個錯誤的測試案例，確認修正前會失敗、修正後通過：

- 單元測試涵蓋得到的（商業邏輯、Context、Entity），寫成單元測試，測試名稱寫出錯誤情境。
- 單元測試涵蓋不到的（頁面、前端腳本、設定檔），寫成手動驗收項目，加進該功能 02-design.md `### 6. 測試` 與 03-tasks.md 對應任務，步驟要能重現當時的錯誤。
- 走本流程以外的錯誤修正（見「什麼時候不走本流程」）也一樣要加，寫進對應的測試專案；沒有對應的功能規格時，在回覆中列出手動驗收步驟。

錯誤修正通常只改一兩行，很容易在之後的修改中被改回去；有了測試，同一個錯誤再發生時會先被抓到，不必等使用者再回報一次。

### 什麼時候不走本流程

本流程用在**新功能**或**改變既有商業規則**的變更。下列變更直接修改程式碼，不建立 `specs/` 資料夾：

- 錯誤修正：程式沒有照既有規格或預期運作。
- 小幅調整：文字、標籤、選項內容、欄位順序、版面樣式這類不改變商業規則的修改。

拿不定時問使用者要不要走本流程，不自行決定。

已完成需求的 `specs/` 文件**不回頭同步**：之後的修改不必更新舊的規格文件，新需求一律以目前的程式碼為準（見第 2 章）。同步舊文件的成本高，而且容易漏改，與其維護一份可能過時的文件，不如以程式碼為唯一的現況。

## 2. 資料夾與編號

- 每個需求一個資料夾：`specs/NNNN-需求中文名/`。
  - `NNNN` 四位數，從 `0001` 開始，接續目前最大的編號。
  - 名稱用中文，例如 `specs/0002-預約提醒/`。
- 資料夾內三份文件：`01-requirement.md`、`02-design.md`、`03-tasks.md`。
- 沒有基準規格：每個需求都是一份獨立的需求評估與系統設計，**以目前的程式碼為準**撰寫。
- 驗收條件編號（`R1`、`AC-1.1`……）在每個需求資料夾內重新從 1 開始。

## 3. 01-requirement.md 需求分析

只談需求，不談實作技術。

標題：`# NNNN 需求中文名 — 需求分析`

章節依序：

| 章節 | 內容 |
|---|---|
| `## 背景` | 現況與要解決的問題 |
| `## 使用者故事` | `- **US-n** 身為〇〇，我想〇〇，以便〇〇。` |
| `## 名詞定義` | 本需求的專有名詞，避免同一件事有兩種說法 |
| `## 欄位` | 有輸入欄位時才寫。依「由誰填寫」分組，每組一張表：`欄位`・`必填`・`格式` |
| `## 驗收條件` | 依需求分組 `### Rn 標題（US-x）`，每條 `AC-n.m` 用 Given／When／Then |
| `## 對既有行為的影響` | 讀過目前的程式碼後，列出會改變的既有行為：`既有行為`・`變更內容`。沒有影響也要寫明 |
| `## 不在範圍內` | 明確排除的項目，防止實作時擴大 |
| `## 已決事項` | `項目`・`決定`，從待決事項移過來時保留原編號（例如 `Q3`） |
| `## 待決事項` | 還沒決定的問題，編號 `Q1`、`Q2`……；不自行假設答案。沒有時寫「目前沒有待決事項」 |

驗收條件範例：

```markdown
### R1 建立訂單（US-1）

- **AC-1.1** 店員可建立訂單
  - Given 店員已登入並屬於該商家
  - When 在建立訂單頁輸入必填欄位，按「建立」
  - Then 建立一張訂單，畫面進入該訂單的明細頁
```

規則：

- **只有需求名稱時先問需求描述**：使用者只給了需求名稱、完全沒有描述時，先問「誰、要做什麼、為什麼」（可附上 `docs/` 裡的設計圖或截圖路徑），不讀程式碼、不建立資料夾，等使用者回答後再撰寫。有描述但不完整時直接撰寫，缺的部分列進「待決事項」。憑需求名稱猜出來的需求會讓審核變成重寫；但描述已經有方向時，把缺的部分整理成待決事項，比反覆問答更快定案。
- **待決事項都要問完**：寫完後在回覆中逐一詢問每個待決事項，附上可選的答案或建議；使用者回答後依答案修改文件，並把該項移到「已決事項」。還有待決事項時，需求分析就還沒完成，不建議進入系統設計。待決事項只列在文件裡容易被略過，未定的需求會一路帶進設計與實作。
- **任何對既有行為的改變都要寫在「對既有行為的影響」**，而且要以實際讀過的程式碼為依據（寫出檔案或頁面名稱）。使用者審核需求時，要能看出這個需求會動到哪些既有的東西。
- 驗收條件要能直接驗證：寫具體的輸入與畫面結果，不寫「正確處理」這類無法檢查的描述。
- **驗收條件是本階段的測試案例**：每個 `Rn` 至少一條 AC。

## 4. 02-design.md 系統設計

依 01-requirement.md 設計，只設計需求中列出的行為，未列出的不做。**物件的寫法、分層、命名遵守專案技術對應的架構規範**；本節只規定文件的結構。

標題：`# NNNN 需求中文名 — 系統設計`

開頭寫「依據：`01-requirement.md`。」，需要時補充本文件的用語。

章節依序：

### 1. 專案架構

- 新增或變更的專案：表格 `專案`・`變更`（含設定檔、資料庫、方案檔）。
- 依賴方向（A → B 表示 A 參考 B），只列新增或有關的。

### 2. 物件模型

- **2.1 物件一覽**：本需求新增或異動的每個物件一張表，`物件`・`專案／位置`・`新增／異動`・`說明`（說明指向細節小節，例如「（§2.3）」）。
  - 列入：Entity、輸入輸出物件、常數／選項類別、Repository 介面、模組入口（例如 .NET 的 Context）、資料存取實作、測試用 Mock。
  - 不列入：頁面與 UI 元件，它們只在「4. 頁面」說明。
  - 表格後寫「共同原則」：本需求套用的架構規則，例如商業邏輯放在哪裡、哪些寫入只能經過哪個方法。
- **之後每個物件一個小節**，包含：
  - `#### 屬性`：表格 `屬性`・`型別`・`對應需求`・`說明`。日期時間屬性放最後，以 `CreateTime`、`UpdateTime` 結尾。
  - `#### 方法`：表格 `方法`・`用途`・`AC`，表格後逐一寫每個方法的規則（步驟、例外、不寫入哪些資料）。沒有方法時寫「無」。
- **商業邏輯寫在擁有它的模組入口方法裡**（例如 .NET 的 Context 方法），不另開「商業規則」章節。規則和執行它的方法放在一起，實作時不用對照兩處。
- 資料存取實作寫出資料表結構。

### 3. 權限與匿名存取

哪些頁面或 API 需要登入、需要什麼角色；有匿名存取時，說明改用什麼方式授權（例如有時效的網址）。設定檔是否需要修改。

### 4. 頁面

每個新增或修改的頁面一個小節，標題寫出頁面路徑、新增／修改、對應 AC，例如 `### 4.3 Companies/Orders/NewPage（新增，AC-1.1–1.4）`。內容：欄位與按鈕、前端驗證、呼叫哪個物件的哪個方法、錯誤訊息、導覽。

### 5. 對既有行為的影響

表格 `項目`・`變更`・`對應 01-requirement.md`。內部變更（資料庫、方案結構、要同步更新的 `CLAUDE.md`）也列出。

### 6. 測試

- 單元測試清單：測試方法名稱與對應 AC 編號。商業邏輯都要有單元測試。
- 手動驗收項目：頁面行為、權限、單元測試涵蓋不到的部分，對應 AC 編號。
- **01-requirement.md 的每條 AC 都要至少對應一項**單元測試或手動驗收，不可遺漏。

### 7. 待確認事項

設計時發現的問題；沒有時寫「無」。

**02-design.md 不寫實作順序**，實作順序寫在 03-tasks.md。

## 5. 03-tasks.md 任務拆解

依 02-design.md 拆解任務，並排出執行順序。

標題：`# NNNN 需求中文名 — 任務拆解`

開頭寫依據與共同規則，例如：

```markdown
依據：`01-requirement.md`、`02-design.md`。依 T1 → T5 的順序實作，每個任務完成後執行建置與相關測試，並把該任務的「完成」打勾。規格有缺漏或矛盾時停下來詢問，不自行補上。
```

每個任務：

```markdown
## T1 標題

- [ ] 完成

內容：

- 要新增或修改的檔案與內容（指向 02-design.md 的小節）

AC：2.1、2.4

單元測試：

- `測試方法名稱`

手動驗收：

- 驗收步驟與預期結果
```

規則：

- **每個任務要能在一次對話內完成**。
- 依依賴順序排列：先領域物件與測試，再資料存取，再頁面，最後整體驗收與文件同步。
- **每個任務都必須有測試案例**：單元測試與手動驗收合計至少一項，不可兩者都寫「無」。單元測試涵蓋不到的（頁面、設定檔、資料庫結構）寫成手動驗收，要有具體步驟與預期結果。
- **02-design.md `### 6. 測試` 的每一項都要分配到某個任務**，不可遺漏。
- 每個任務列出 AC 編號；沒有對應 AC 時寫「無」並說明原因。

## 6. 程式開發

- **一次實作一個任務**，依 03-tasks.md 的內容，不多做。使用者要求實作全部任務時，依 03-tasks.md 的順序逐一進行：一個任務完成、測試通過、打勾後，才開始下一個。
- 每個任務完成後執行建置與該任務的測試案例，回報結果；通過後把該任務的 `- [ ] 完成` 改成 `- [x] 完成`。
- 測試失敗或需要問使用者時就停下來，不跳過去做下一個任務。
- **規格有缺漏或矛盾時停下來問**，不自行補上未規定的行為。
- 實作中發現需要改設計：先提出，經使用者同意修改 02-design.md（必要時 01-requirement.md）後，依[流程](#1-流程)跑過每個階段的測試案例（文件比對與執行測試），全部通過再繼續實作。

## 7. 工程師的指令範例

### 開始需求分析

```
為新需求建立 specs/NNNN-<需求中文名>/01-requirement.md。
```

只給需求名稱時，AI 會先問需求描述（誰、要做什麼、為什麼）；也可以直接接在指令後面寫出來。寫完後，AI 會逐一詢問每個待決事項，直到全部決定。

### 審核來回（任何文件都適用，可重複多次）

```
修改 01-requirement.md：
- AC-2.3 改成 <...>
- 待決事項 Q1 決定為 <...>，移到已決事項
- 「<某項>」移到不在範圍內
```

審核時引用編號（`AC-x.y`、`Q1`、`§2.3`），修改範圍才會精準。

### 系統設計（建議開新對話）

```
請依 specs/NNNN-<需求中文名>/01-requirement.md 建立 02-design.md。
```

AI 會套用專案技術對應的架構規範；01-requirement.md 有缺漏或矛盾時，會先停下來問。

### 任務拆解

```
請依 specs/NNNN-<需求中文名>/02-design.md 建立 03-tasks.md。
```

AI 會把設計拆成每個都能在一次對話內完成的任務，並排好順序；02-design.md 有缺漏或矛盾時，會先停下來問。

### 程式開發

```
依 specs/NNNN-<需求中文名>/03-tasks.md 實作全部任務。
```

AI 會依序一次做一個任務，測試通過、打勾後才做下一個；測試失敗或規格有疑問時，會停下來問。只做單一任務時，把「全部任務」改成任務編號，例如「實作 T2」。
