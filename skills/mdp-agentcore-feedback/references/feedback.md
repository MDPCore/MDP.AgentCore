# MDP.AgentCore 規範回饋

使用 AI 開發時，使用者對 AI 產出的修正，或 AI 遇到規則沒涵蓋的情況，常常代表一條還沒寫進規範的規則。本流程讓 AI 在這些時候判斷：要不要成為規範？要的話，提議寫進哪裡，等使用者確認後才寫入。

規範就這樣在日常開發中逐步補齊，而且只有一個地方：MDP Skill 的 references 文件。

## 1. 何時啟動

### 使用者修正了 AI 的產出

使用者修正了 AI 產出的程式碼、設計或規格文件，例如：

- 「不對，這裡要用 `== false`」
- 「Entity 不要放這個方法，移到 Context」
- 「需求分析不要自己決定退訂規則，放待決事項」

不只是明確說「錯了」：使用者自己動手改了 AI 的產出，或否決 AI 的做法並說明理由，也算。

**先照修正改好，再進行判斷。** 回饋流程不能耽誤手上的工作。

### 遇到規則沒涵蓋的情況

依 MDP Skill 工作時，遇到規則沒寫到的情況：

1. **依相關規則的理由判斷**怎麼做，完成手上的工作；不要照字面硬套，也不要停下來等使用者決定。
2. 在回覆中說明這裡是依哪條規則的理由判斷的。
3. 依第 3 章判斷是否該補進規範。

規則附上的理由（見第 5 章），就是為了讓規則沒寫到的情況也能推論；但推論的結果只在這次對話有效，要寫進規範才能讓每個人、每次都一致。

### 專案設定

使用者修正 AI 的產出時，通常不會提到「規範」或「回饋」；AI 遇到規則沒涵蓋的情況，也不會想到要載入本流程。只靠 Skill 的說明不一定能觸發，每個使用 MDP Skill 的專案，都要在專案 `CLAUDE.md` 的規則段落加上這一行：

```markdown
- 使用者修正你產出的程式碼、設計或規格文件，或你遇到 MDP Skill 規則沒涵蓋的情況時，使用 `mdp-agentcore-feedback` Skill 判斷是否該成為 MDP Skill 的規則；不要把這類修正存進記憶。
```

`CLAUDE.md` 每次對話都會載入，比 Skill 說明更可靠；Skill 收進 MDP.AgentCore plugin 後也沒辦法替專案加上這一行，要由專案自己加。

## 2. 規範在哪裡

本流程適用所有 MDP Skill，也就是以 `mdp-{平台}core-{用途}` 命名的 Skill，包括本 Skill。下表列出目前的 MDP Skill；之後新增的 MDP Skill 不必等列進表格，同樣適用。

每個 MDP Skill 的規則都寫在它資料夾裡的 references 文件，這是規則的唯一來源：

| Skill | 範圍 | 規則文件 |
|---|---|---|
| `mdp-netcore-architecture` | .NET 程式碼與物件設計 | `references/architecture.md` |
| `mdp-javacore-architecture` | Java 程式碼與物件設計 | `references/architecture.md` |
| `mdp-vuecore-architecture` | Vue 程式碼與元件設計 | `references/architecture.md` |
| `mdp-pythoncore-architecture` | Python 程式碼與物件設計 | `references/architecture.md` |
| `mdp-agentcore-specification` | 功能規格流程與文件格式 | `references/specification.md` |
| `mdp-agentcore-feedback` | 本流程 | `references/feedback.md` |

Skill 放在專案的 `.claude/skills/{Skill}/`，或 MDP.AgentCore plugin 裡。找不到對應的 Skill 時，告訴使用者，不自行建立。

專案特有的事不屬於 MDP Skill，寫在該專案的 `CLAUDE.md`。

## 3. 判斷

先讀對應的規則文件，找出和這個修正（或沒涵蓋的情況）有關的章節，再判斷屬於哪一種：

| 情況 | 處理 |
|---|---|
| 通用規則，以後每個專案、每個功能都該這樣做 | 提議**新增**規則 |
| 和現有規則衝突 | 提議**修改**那條規則，引用原文。先問清楚使用者是要改規則，還是這次例外 |
| 規則已經寫了，是 AI 沒照做 | **不新增**規則；指出是哪條規則，提議改寫成更不容易被忽略的措辭（例如補理由、補範例） |
| 只適用這個專案 | 不提議改 Skill；建議寫進專案 `CLAUDE.md` |
| 只適用這一次（需求內容、個別情況） | 不提議 |

拿不定是哪一種時，直接問使用者，不要猜。

**不存進記憶（memory）。** 規範類的修正一律走本流程。記憶只在使用者自己的電腦生效，團隊其他人和其他專案看不到；寫進 Skill 才能讓每個人、每次對話都套用。

## 4. 提議

在回覆最後，用固定格式提出，一次一條：

> 這個修正看起來是通用規則，要加入規範嗎？
> - 位置：`mdp-netcore-architecture` → `references/architecture.md` → 10. Entity 設計規範
> - 新增：「修改既有 Entity 時若缺少 `CreateTime`／`UpdateTime`，直接補上……」
> - 理由：……

- **位置**寫到章節。
- **新增／修改**寫出完整的規則句子；修改時同時列出原文與新文。
- **理由**說明這條規則防止什麼問題；規則不是一看就懂時，理由也會寫進規則文件。

一次修正牽涉多條規則時，逐條列出，讓使用者可以分別同意。

## 5. 寫入

- **使用者明確同意後才寫入**；沒有回應或只是繼續別的工作，不算同意。
- **規則不是一看就懂時才附上理由**，直接接在規則後面寫成一般句子，不加「理由：」標籤，文字簡單易懂就好；寫法和該章既有規則一致，必要時附範例。理由讓 AI 遇到規則沒涵蓋的情況時能依理由判斷（見第 1 章）。放在相關的位置，不要全部堆在章節最後。
- **不出現任何專案的名稱。** 寫進 MDP Skill 的規則、範例與 evals 都不出現專案特有的名稱（產品名、公司或領域前綴、專案路徑）；範例改用 `MDP.Orders`、`MDP.Shop` 這類名稱，或 `{Domain}`、`{App}` 佔位符，evals 用「Orders 模組」這類描述，不寫死專案路徑。MDP Skill 會收進 MDP.AgentCore plugin，給所有團隊和專案使用；範例裡有某個專案的名稱，讀的人會以為規則只適用那個專案，AI 也可能把那個名稱照抄進別的專案。
- 規則改變了 Skill 的觸發範圍時，一併更新該 Skill 的 `SKILL.md` description。
- 該 Skill 有 `evals/` 測試案例時，一併新增或修改評分項目，讓之後的測試能檢查這條規則。evals 跟著規則修改，不必另外等使用者同意，寫入後回報即可。
- 寫入後回報改了哪個檔案、哪一章。
